## P1 — 质量（避免污染知识库）

### P1.1 — 约束里有垃圾（4/8 条是 fallback 噪音）

**原始问题**：
`api_constraint.json` 共 8 条约束，其中 4 条是 `"Avoid this runtime failure pattern: <CUDA_ERROR_ILLEGAL_ADDRESS...>"`。
来源：`loop_c/constraint_builder.py:299` 的兜底分支——把 CUDA/Taichi/OOM 等内部错误原样贴成 API 约束。
例如 CUDA 驱动错误被当成了 `genesis.Scene.step` 的"使用约束"。

**用户回应**：
> 约束里的垃圾是之前回路 C 的一次测试的产物，当时发现了有垃圾内容然后反馈给系统对回路 C 完善，不过垃圾内容忘记清理了。后续跑回路 C 打算先清空 `api_constraint.json` 的内容。

**跟进回复**：
清空旧文件应该做，但只清空不够——回路 C 再跑还会产生一样的垃圾，因为 `constraint_builder.py:299` 的兜底逻辑没有改。建议两步一起：
1. **清空** `api_constraint.json`
2. **删掉** `constraint_builder.py:299` 的 `cons.append(f"Avoid this runtime failure pattern: {msg}")`，改成 `continue`（不产出约束而非产出垃圾）。遇到 CUDA/Taichi/OOM 等非 API 误用错误时直接跳过。

**当前状态**：待执行清空 + 删除垃圾 fallback。

### P1.2 — 三个 Gate 在 LLM 不可用时一律 pass=true（fail-open）

**原始问题**：
`gates.py:113/123/187/199/264/274`。三个 gate 在 LLM 不可用或调用失败时一律返回 `pass=True`。
质量门控静默降级成"全收"——对自增长知识库是反模式。

**用户回应**：
> gate 的意见我不太明确，我不太清楚应该是静默还是不静默。

**跟进回复（推荐 fail-closed）**：

| 模式 | 行为 | 风险 |
|---|---|---|
| fail-open（当前） | LLM 不可用时全部放行 | 静默污染知识库，你不知道什么东西没审就进了 |
| fail-closed | LLM 不可用时全部拒进 rejected/ | 好东西暂时被挡，但可追踪、可补审 |
| 折中 | reject + 打标记 `llm_unavailable: true`，下次重跑时优先重审 | 实现最复杂 |

推荐 **fail-closed**，三个理由：
1. **知识库污染比延迟更难修**。垃圾进库后基本发现不了（除非人工抽检），但会通过检索悄悄毒害每一轮代码生成。rejected/ 里的东西随时能翻、能补审。
2. **LLM 不可用的概率极低**。DeepSeek API SLA 比本地开发机的电源还稳——更多会因为代码 bug 进这个路径。出 bug 时应宁可拒掉小批量，好过大量灌入未审内容。
3. **rejected/ 目录本来就是为这个设计的**，只是 gate 还没真正往里面写过东西。

如果觉得太激进，可以**只对回路 C 用 fail-closed**（回路 C 的质量问题最严重，约束进了库就很难发现错误），A/B 保持 fail-open。

**当前状态**：等待用户拍板 fail-open 还是 fail-closed（或至少回路 C fail-closed）。

## P2 — 健壮性 / 完善

### P2.1 — loop_b/judge.py 用了不同的 LLM provider

**原始问题**：
`judge.py` 用 ChatAnywhere + `CHAT_API_KEY` + `gemini-3-pro-preview`，而系统其余模块统一用 DeepSeek。
另外 `judge.py:23-26` 模块级硬实例化 `OpenAI(api_key=os.getenv("CHAT_API_KEY"), ...)`——import 时就执行，key 没配就静默失败。

**用户回应**：
> 这个 judge.py 是专门让更强的模型作为 judge 的，是特意这样做的，你觉得不行吗还是？

**跟进回复**：
**用意完全正确**——judge 负责"这条知识值不值得入库"，犯错成本高（误收 vs 漏收），用更强模型是对的。

我有问题的不是"用不同模型"，而是三个**实现脆弱点**：
1. **模块级硬实例化**（`judge.py:23`）。改成懒加载（类似 `query_rewriter._get_llm()` 模式）更稳，key 后设也能拿到。
2. **失败无可见性**。processor 调 `analyze_error()` 时不知道 judge 初始化状态；如果 key 没配或过期，analyze_error 静默返回 None（`judge.py:122`），processor 就跳过——等于整个回路 B 静默失效。建议失败时打 warning + 写入 rejected/。
3. **两套 judge 配置分散**（judge.py 的 ChatAnywhere + loop_c JudgeLLM 的 OpenAI/Gemini）。统一到一个 `.env` 变量（如 `JUDGE_MODEL` / `JUDGE_API_KEY`）让维护更简单。

**总结**：用更强模型 judge ——对。改懒加载 + 加失败可见性——建议做。

**当前状态**：待实现懒加载 + 失败可见性。

### P2.4 — 没记录检索归因

**原始问题**：
设计文档的 log 格式含 `rag_knowledge_ids`（"检索到的知识条目 id → 是否被代码采用 → 是否跑通"），但 `run_and_collect.py` 没存这个字段，`agent.solve()` 也没暴露检索到的条目 id。
这卡住了 roadmap 阶段 0.3 的 utility_score（每条知识的"实战战绩"）。

**用户回应**：
> 没看懂你说的"没记录检索归因"。

**跟进回复（一句话说明）**：
**Agent 检索到了哪些知识条目（如 "unit_042"、"api_Sphere"），这些 id 目前没有记录到 execution_log 里。**
具体路径：
- `agent.solve()` 调 `rag.search()` 拿到 knowledge_list（每条有内部 id，ChromaDB 返回的）
- 代码生成 + 执行
- `run_and_collect.py` 写 execution_log
- **但日志里没有记录"这轮命中了哪些知识条目"**

为什么重要：roadmap 要做的 utility_score（计算每条知识的被采用次数 × 成功率）依赖这个数据。没有归因日志，你不知道哪条知识有用哪条是占位。

实现很小：`agent.solve()` 返回值加 `knowledge_ids` 字段 + `run_and_collect.py` 落盘时带上。

**当前状态**：待实现。

### 核心架构变更：无 LLM Judge + 人工审核流程

**改前三文件**：

| 文件 | 改前 | 改后 |
|---|---|---|
| `gates.py` | 三个 gate 各含 LLM PROMPT + `_init_client()` + `_ask_llm()`，失败时 fail-open（pass=True） | 移除全部 LLM 代码。`review()` 一律返回 fail-closed（pass=False, pending=True）。新增 `format_for_review()` 生成 markdown 审查区块 |
| `loop_b/judge.py` | `analyze_error()` 调用 ChatAnywhere + gemini-3-pro-preview 分析错误 | 改为纯收集：返回原始 code + error_log + query_context，供人工分析 bad_pattern |
| `processor.py` | 调 gate.review() 后直接写入 knowledge_base JSON | 不调 gate。收集候选 → 生成 `pending_review_TIMESTAMP.md` + `pending_candidates_TIMESTAMP.json`。新增 `--approve` 模式，人工审核通过后执行入库 |

**新 workflow**：

```bash
# Step 1: 跑生成+执行+收集
python feedback_loop/run_and_collect.py --prompts benchmark/query.json

# Step 2: 处理日志 → 生成待审文档（不自动入库）
python feedback_loop/processor.py --log workspace/logs/execution_log_*.jsonl
# → 输出: workspace/pending_reviews/pending_review_YYYYMMDD_HHMMSS.md
# → 输出: workspace/pending_reviews/pending_candidates_YYYYMMDD_HHMMSS.json

# Step 3: 将 pending_review.md 发到网页端 Judge 人工审核

# Step 4: 审核通过后入库
python feedback_loop/processor.py --approve workspace/pending_reviews/pending_candidates_YYYYMMDD_HHMMSS.json --ids "A:0,A:2,B:1,C:all"

# Step 5: 重新灌库
python rag_engine.py
```
